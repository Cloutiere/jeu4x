# Le jeu 4X « Cyber Revolution » — Présentation technique

*Document de présentation pour analyse externe. Le projet est développé en mode agentique : un concepteur non-codeur pilote, des agents d'implémentation codent par tranches cadrées (handoffs), un agent « pilote » tient la documentation et l'acceptation.*

## Le jeu en quelques paragraphes

C'est un **jeu de stratégie 4X au tour par tour, multijoueur 1v1 principalement asynchrone**, clone fidèle et allégé de *Sid Meier's Civilization Revolution* (version console 2008). Deux joueurs s'affrontent sur une **carte hexagonale de 40×40 cases** ; chacun joue son tour quand il veut (les parties se jouent sur plusieurs jours), et les **tours sont simultanés** : les ordres des deux joueurs sont résolus ensemble en fin de tour, ce qui garantit l'équité sans imposer de synchronisation.

Le jeu reprend les systèmes du modèle : **46 technologies** organisées en arbre et en 4 ères ; **16 civilisations** avec avantage de départ, bonus d'ère cumulatifs et unités uniques ; villes qui produisent nourriture/production/commerce et croissent (consommation alimentaire, seuils linéaires) ; **22 ressources de terrain** révélées progressivement par les technologies ; **merveilles du monde** exclusives à obsolescence globale ; six classes de **Personnages Illustres** avec choix consommation/installation ; gouvernements avec Anarchie ; barbares, huttes et **artefacts** tirés au sort ; une **économie d'or** complète (trésorerie, achat instantané, paliers économiques) ; l'**espionnage** (vol d'or et de Personnages, duels d'espions) ; et l'**arme nucléaire** (un seul ICBM par partie, défense antimissile). Quatre voies de victoire coexistent : **domination** (capturer la capitale adverse), **culture** (20 jalons puis Nations Unies), **scientifique** (composants du vaisseau spatial) et **économique** (20 000 or puis Banque mondiale).

**Particularité visuelle** : le jeu migre du thème historique vers un **thème « monde virtuel nanotechnologique »**. Le terrain est rendu en **vraie 3D** (Three.js) avec un langage visuel spécifique : chaque tuile affiche son **potentiel** en glyphes néon (bus de données = nourriture, microprocesseurs = production, barrettes RAM = commerce), le rendement actif étant « allumé » ; les ressources sont des **cartes insérées dans des slots**, visibles mais neutres tant que la technologie associée n'est pas découverte ; les villes sont des **Nœuds Serveur (Mainframes)** qui grossissent avec la population et portent un module par bâtiment. Les unités sont des sprites 2D projetés sur le terrain 3D (architecture hybride), avec migration progressive vers des modèles 3D.

## Le stack technologique en détail

**Architecture générale.** Application web desktop-only organisée en **monorepo pnpm** avec **Turborepo** : `apps/web` (client), `apps/server` (backend), `packages/rules` (moteur de règles pur). Tout est en **TypeScript** strict. Conventions : français dans les documents et l'interface, anglais dans le code et les identifiants.

**Moteur de règles — `packages/rules` (le cœur).** Un module **TypeScript purement fonctionnel, sans aucune entrée/sortie** (zéro réseau, zéro DOM, zéro horloge) : il prend un état, des ordres et renvoie les événements du tour. Le déterminisme est absolu : **RNG mulberry32 seedé** (aucun `Math.random`, aucun `Date.now`), parcours triés. Toutes les données de jeu sont **data-driven** (fichiers JSON versionnés : technologies, unités, bâtiments, merveilles, ressources, civilisations, croissance, gouvernements, économie, artefacts, espionnage, terrain, spécification visuelle 3D) — recalibrer le jeu est de l'édition de données, pas du code. L'état porte un **`schemaVersion`** (18) avec une chaîne de migrations testées, et le couple `{état, ordres, graine}` permet de **rejouer toute résolution à l'identique** (crash-recovery idempotent). Une spécification normative (`RULES.md`, règles numérotées R-xx) fait foi et **chaque règle a au moins un test qui la cite**.

**Backend — Cloudflare Workers + Durable Objects.** Deux types de Durable Objects : un `LobbyDO` (parties publiques, codes d'invitation) et un **`GameDO` par partie**, point d'autorité unique : il détient l'état, accepte les ordres (validation de forme et de propriétaire avant résolution), **résout simultanément les tours** via le moteur, et diffuse les événements aux clients par **WebSocket en mode hibernation** (coût quasi nul entre les tours). Les clients ne sont **pas autoritaires** : chaque joueur ne reçoit que l'état **filtré par son brouillard de guerre**. Un **mode solo contre un bot** est supporté : le bot est un joueur interne du GameDO (politique déterministe, RNG dédié). Authentification **OAuth Google et Discord** réelles (sessions par cookie), hébergement **Cloudflare Workers + Static Assets** même origine, budget d'hébergement ~5 $/mois.

**Frontend — Svelte 5 + rendu hybride 2D/3D.** SPA **Svelte 5** (runes) servie par Vite, navigation par routes hash (lobby, partie, et des **labos de calibrage** : génération procédurale, banc 3D, atelier d'assets). Le rendu de la carte est **hybride** : le **terrain est une scène Three.js instanciée** (16 000 objets en ~50 draw calls, 60 FPS sur 40×40), les **unités restent des sprites PixiJS v8** projetés sur le terrain par la caméra partagée (picking analytique hex→écran partagé entre les deux canevas). L'interaction (sélection, chemins, ordres à la souris) passe par des **fonctions pures testées**, identiques en 2D et 3D.

**Qualité et livraison.** **868+ tests Vitest** (moteur pur, serveur, composants web), typecheck strict partout, scripts e2e Node pilotant deux clients WebSocket réels (y compris victoires complètes et migrations d'état), et une **session GUI vs bot** exigée à chaque livraison. **CI/CD GitHub Actions** : chaque push sur `main` est déployé automatiquement sur la prod. Les assets (sprites PNG) sont produits par un **pipeline Python procédural** (`generate.py` + sync-art), reproductible.

**Développement agentique.** Le code est écrit par des agents d'implémentation guidés par des documents de mission (handoffs) et des spécifications de recherche rédigées par le concepteur ; chaque livraison fait l'objet d'un rapport, d'une vérification indépendante et d'une acceptation du concepteur. Les documents du projet sont organisés (`docs/recherche/`, `docs/historique/`, index) et l'état courant est centralisé (`PROJET.md`).
